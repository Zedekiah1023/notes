# Mooncake前360条：全局4%计算额度的可行性

用户要求保留原input长度，把整批input的4%作为总未命中计算额度，
跨请求分配出重读轻算A、轻读重算B、零读计算C，并探索重读重算D。
不使用output_length、hash_ids或每请求固定4%的命中规则。

## 预算与约束

对每条请求，n为原input_length，h为远端缓存前缀，u=n-h为新计算token。
所有请求都保留原n，h必须为16的倍数，u至少为1。C要求h=0。
N=Σn，总计算量不得超过N/25；在block16下选择不超预算且最接近的可行整数。
当前N=5117755，理论额度204710.2，使用204699，比例约3.999781%。
精确4%非整数不可实现；保持原长度又要求整块命中时，总u只能与N同余mod16。

## 两个候选

按(input_length,原行号)排序，仅决定预算分配，回放顺序和计划到达时刻不重排。

- ABC：最短30条为C，随后90条为B，其余240条为A。
- ABCD：保留上述B/C，再将最长20条A改为D，余下220条为A。
- A：只计算当前引擎和块对齐所需的最少1–16个token，其他均读取。
- C：全部input作为新计算，不读取外部KV。
- D：每条分配不超过2048、满足block16的计算量，约2033–2046。
- B：在保留至少一个缓存块的前提下，按各请求可承接额度比例分配剩余预算，
  使用最大余数法以16-token单位补齐。全局总u严格一致，不额外添加计算额度。

这些类别是人工读算成本分类，不是TFS运行期按P75得到的分类。
命中量为人工设定，不代表Mooncake真实缓存命中。保持当前GLM公式、TP1/DP8/EP8、
12实例、120GB/s、block16、batch≤4、8192token预算、78层和K=1。
新h/u需要重算T0与期限，不沿用旧96%实验的画像或展示标签。
